Language Basics
Variables & Types
JS/TS uses dynamic typing by default. TypeScript adds a structural type system on top — it's checked at compile time only, the runtime is still plain JS.
Variable Declaration breaking difference
Java
int count = 0;
final String name = "atlas";
List<String> items = new ArrayList<>();

// var available since Java 10 (local only)
var inferred = 42;
C++
int count = 0;
const std::string name = "atlas";
std::vector<std::string> items;

// auto since C++11
auto inferred = 42;
JavaScript
let count = 0;              // mutable, block-scoped
const name = "atlas";       // immutable binding
const items = [];

// no type annotation — inferred at runtime
let inferred = 42;
TypeScript
let count: number = 0;
const name: string = "atlas";
const items: string[] = [];

// type inferred — annotation optional here
let inferred = 42; // : number
Primitive Types breaking difference JS has one number type for everything
Java
int     i = 42;
long    l = 9_000_000_000L;
double  d = 3.14;
boolean b = true;
char    c = 'x';
String  s = "text"; // object, not primitive
C++
int          i = 42;
long long    l = 9000000000LL;
double       d = 3.14;
bool         b = true;
char         c = 'x';
std::string  s = "text";
JavaScript
// ONE number type — no int/float/double
let i = 42;          // number
let d = 3.14;        // also number
let b = true;        // boolean
let s = "text";      // string (primitive)
let big = 9n;        // BigInt for large integers
let n = null;        // intentional empty
let u;               // undefined — not assigned
TypeScript
// ONE number type — no int/float/double
let i: number = 42;
let d: number = 3.14;
let b: boolean = true;
let s: string = "text";
let big: bigint = 9n;
let n: null = null;
let u: undefined = undefined;
⚠ null vs undefined — JS has both. null means "intentionally empty". undefined means "never set". You'll encounter both. TypeScript's strict mode makes the compiler catch unhandled cases.
Union / Optional Types similar concept
Java
Optional<String> maybeStr = Optional.of("hello");
maybeStr.ifPresent(v -> System.out.println(v));
C++
std::optional<std::string> maybeStr = "hello";
if (maybeStr) {
  std::cout << *maybeStr;
}
JavaScript
// no built-in optional type — use null/undefined
const maybeStr = "hello"; // or null
if (maybeStr) {
  console.log(maybeStr);
}
// optional chaining: obj?.prop?.nested
TypeScript
// union type replaces Optional<T>
let maybeStr: string | null = "hello";
if (maybeStr !== null) {
  console.log(maybeStr); // narrowed to string
}
// shorthand optional param: value?: string
Language Basics
Functions
Functions are first-class values in JS/TS. They can be passed, stored, and returned like any other value — no functional interface boilerplate needed.
Function Declaration similar concept
Java
public String greet(String name) {
  return "Hello, " + name;
}

// static method
public static int add(int a, int b) {
  return a + b;
}
C++
std::string greet(std::string name) {
  return "Hello, " + name;
}

int add(int a, int b) {
  return a + b;
}
JavaScript
function greet(name) {
  return `Hello, ${name}`;
}

// arrow function (no own `this`)
const add = (a, b) => a + b;

// default params
function inc(n, by = 1) {
  return n + by;
}
TypeScript
function greet(name: string): string {
  return `Hello, ${name}`;
}

// arrow function
const add = (a: number, b: number): number => a + b;

// default + optional params
function inc(n: number, by: number = 1): number {
  return n + by;
}
Functions as Values (Lambdas) breaking difference No SAM / functional interface needed
Java
Function<String, Integer> len = s -> s.length();

List<String> names = List.of("bob", "alice");
names.stream()
  .map(s -> s.toUpperCase())
  .forEach(System.out::println);
C++
std::function<int(std::string)> len
  = [](std::string s) { return s.length(); };

std::vector<std::string> names = {"bob", "alice"};
std::for_each(names.begin(), names.end(),
  [](std::string& s) { std::cout << s << "\n"; });
JavaScript
// functions are plain values, no wrapper type
const len = s => s.length;

const names = ["bob", "alice"];
names
  .map(s => s.toUpperCase())
  .forEach(s => console.log(s));
TypeScript
// function type inline, no interface needed
const len: (s: string) => number = s => s.length;

const names: string[] = ["bob", "alice"];
names
  .map(s => s.toUpperCase())
  .forEach(s => console.log(s));
⚠ Arrow functions and this — Arrow functions do not have their own this. They capture the this of the surrounding scope. Regular function declarations have their own this, which changes based on how they're called. This is a major source of bugs for Java/C++ devs.
Language Basics
Classes & OOP
JS classes are syntax sugar over prototype chains. The mental model is different even if the syntax looks familiar.
Class Definition similar syntax different runtime model
Java
public class Animal {
  private final String name;

  public Animal(String name) {
    this.name = name;
  }

  public String speak() {
    return this.name + " says ...";
  }
}
C++
class Animal {
  std::string name;
public:
  Animal(std::string n) : name(n) {}

  std::string speak() {
    return name + " says ...";
  }
};
JavaScript
class Animal {
  // private field (modern JS)
  #name;

  constructor(name) {
    this.#name = name;
  }

  speak() {
    return `${this.#name} says ...`;
  }
}
TypeScript
class Animal {
  constructor(private readonly name: string) {}
  // shorthand: declares + assigns in one line

  speak(): string {
    return `${this.name} says ...`;
  }
}
Inheritance similar
Java
public class Dog extends Animal {
  public Dog(String name) {
    super(name);
  }

  @Override
  public String speak() {
    return super.speak() + " woof";
  }
}
C++
class Dog : public Animal {
public:
  Dog(std::string n) : Animal(n) {}

  std::string speak() override {
    return Animal::speak() + " woof";
  }
};
JavaScript
class Dog extends Animal {
  constructor(name) {
    super(name); // must call super first
  }

  speak() {
    return super.speak() + " woof";
  }
}
TypeScript
class Dog extends Animal {
  constructor(name: string) {
    super(name);
  }

  speak(): string {
    return super.speak() + " woof";
  }
}
Language Basics
Interfaces / Contracts
TypeScript uses structural typing — if a value has the right shape, it satisfies the interface, regardless of whether it explicitly declares it. Java uses nominal typing.
Defining & Implementing Interfaces structural vs nominal
Java
interface Printable {
  String render();
}

// must explicitly declare implements
class Report implements Printable {
  public String render() {
    return "report content";
  }
}
C++
// C++ uses pure virtual for interfaces
class Printable {
public:
  virtual std::string render() = 0;
  virtual ~Printable() = default;
};

class Report : public Printable {
  std::string render() override {
    return "report content";
  }
};
JavaScript
// no interfaces at runtime — duck typing
// if it has render(), it's "Printable"
const report = {
  render() { return "report content"; }
};

// JSDoc can annotate shape (optional)
/** @param {{ render(): string }} printable */
function print(printable) {
  console.log(printable.render());
}
TypeScript
interface Printable {
  render(): string;
}

// no implements needed — structural match is enough
const report = {
  render(): string { return "report content"; }
};

function print(p: Printable) {
  console.log(p.render()); // ✓ report satisfies it
}
Structural typing means you can pass a plain object literal where an interface is expected, as long as the shape matches. No boilerplate class needed. TypeScript will tell you at compile time if the shape is wrong.
Language Basics
Generics / Templates
TypeScript generics look like Java generics syntactically. C++ templates are more powerful but more complex. TS generics are erased at compile time — no reification.
Generic Functions & Types similar syntax (TS)
Java
public <T> T first(List<T> items) {
  return items.get(0);
}

public <T extends Comparable<T>> T max(T a, T b) {
  return a.compareTo(b) > 0 ? a : b;
}
C++
template<typename T>
T first(std::vector<T>& items) {
  return items[0];
}

template<typename T>
T max(T a, T b) {
  return a > b ? a : b;
}
JavaScript
// no generics — just works on any value
function first(items) {
  return items[0];
}

// no constraint possible without runtime check
function max(a, b) {
  return a > b ? a : b;
}
TypeScript
function first<T>(items: T[]): T {
  return items[0];
}

// constrained generic
function max<T extends { valueOf(): number }>(a: T, b: T): T {
  return a.valueOf() > b.valueOf() ? a : b;
}
Language Basics
Error Handling
JS has no checked exceptions. You can throw anything — strings, objects, numbers. TypeScript doesn't type-check what's thrown.
try / catch / throw gotcha catch(e) has no type in JS
Java
try {
  riskyOp();
} catch (IOException e) {
  // typed catch — only catches IOException
  log(e.getMessage());
} finally {
  cleanup();
}
C++
try {
  riskyOp();
} catch (const std::exception& e) {
  std::cerr << e.what();
} catch (...) {
  // catch anything
}
JavaScript
try {
  riskyOp();
} catch (e) {
  // e is unknown type — could be anything
  if (e instanceof Error) {
    console.error(e.message);
  }
} finally {
  cleanup();
}
TypeScript
try {
  riskyOp();
} catch (e) {
  // e is `unknown` in strict mode
  if (e instanceof Error) {
    console.error(e.message); // narrowed here
  }
} finally {
  cleanup();
}
Language Basics
Async & Concurrency
JS is single-threaded with an event loop. There are no real threads. Async is cooperative via Promises — not preemptive. async/await is syntactic sugar over Promises.
Async Operations completely different model
Java
// CompletableFuture (Java 8+)
CompletableFuture<String> future =
  CompletableFuture.supplyAsync(() -> fetchData());

future
  .thenApply(String::toUpperCase)
  .thenAccept(System.out::println);
C++
// std::async + std::future
std::future<std::string> fut =
  std::async(std::launch::async, fetchData);

// blocks calling thread
std::string result = fut.get();
JavaScript
// async/await — no threads, event loop
async function loadData() {
  try {
    const result = await fetchData();
    console.log(result.toUpperCase());
  } catch (e) {
    console.error(e);
  }
}

// parallel: Promise.all
const [a, b] = await Promise.all([fa(), fb()]);
TypeScript
// Promise<T> is the typed return
async function loadData(): Promise<void> {
  try {
    const result: string = await fetchData();
    console.log(result.toUpperCase());
  } catch (e) {
    console.error(e);
  }
}

const [a, b] = await Promise.all([fa(), fb()]);
No threads. If you block the event loop (e.g. with a synchronous loop crunching numbers for 5 seconds), everything stops — UI, network, timers. CPU-bound work goes in a Worker thread. I/O is always async and non-blocking.

const sum: number = nums
  .filter(n => n % 2 === 0)
  .reduce((acc, n) => acc + n, 0);

Modules & Packages
ES Modules are the standard. Each file is its own module. Exports are explicit — nothing is public by default.
Exporting & Importing different model
Java
// visibility via access modifiers
// package com.example.utils;
public class MathUtils {
  public static int add(int a, int b) {
    return a + b;
  }
}

// import com.example.utils.MathUtils;
import com.example.utils.MathUtils;
C++
// mathutils.h
#pragma once
int add(int a, int b);

// mathutils.cpp
#include "mathutils.h"
int add(int a, int b) { return a + b; }

// consumer.cpp
#include "mathutils.h"
JavaScript
// mathUtils.js
export function add(a, b) { return a + b; }
export const PI = 3.14159;

// default export (one per file)
export default class Calculator { ... }

// consumer.js
import Calculator, { add, PI } from './mathUtils.js';
TypeScript
// mathUtils.ts — same syntax, plus types
export function add(a: number, b: number): number {
  return a + b;
}
export const PI: number = 3.14159;
export type { MyType }; // type-only export

// consumer.ts
import { add, PI } from './mathUtils';
Key Differences
Conceptual Gaps
These aren't syntax differences. They're things that require a genuine mental model shift.
  • Type system Java and C++ use nominal typing — a class IS its type. TypeScript uses structural typing — a value is compatible with a type if its shape matches, regardless of where it came from. Two unrelated classes with the same fields are interchangeable in TS.
  • Compilation target TypeScript types are erased completely at compile time. At runtime, you're running plain JavaScript. You cannot inspect types at runtime — no instanceof MyInterface checks, no reflection on generics. TS is a linter that disappears.
  • Concurrency model JS is single-threaded with a cooperative event loop. There is no preemption. Async/await is cooperative yielding, not thread switching. Long synchronous operations block everything. Think of it as Node being an event loop, not a thread pool.
  • Prototypes Class syntax is sugar over prototype chains. Objects delegate to their prototype at runtime. This is why you can add methods to existing classes (monkey-patching), and why this context is dynamic. Class in JS is not the same as class in Java.
  • Equality == does type coercion ("0" == 0 is true). Always use === for comparison. This trips up almost every Java/C++ dev. Just never use ==.
  • Scope & hoisting var is function-scoped and hoisted. Always use const or let (block-scoped). var is legacy — avoid it entirely. Pretend var doesn't exist.
  • this binding this in JS is determined by how a function is called, not where it's defined. Arrow functions capture the outer this lexically. Regular functions get their own this from the call site. This is the single biggest source of JS bugs for OOP devs.
  • No overloading JS has no method overloading by signature. You get one function with a given name. TypeScript has overload signatures for type checking, but the runtime implementation is a single function that branches manually. Use optional params or union types instead.
  • Memory management Garbage collected, like Java. No manual memory management. No destructors called at predictable times. Coming from C++, forget RAII — there's no deterministic cleanup.

Gotchas
Things that look familiar but aren't. Read these before you debug for two hours.
Equality trap gotcha
Java
1 == 1          // true
"a".equals("a") // true (value equality)
"a" == "a"      // true (interned) — don't rely on it
C++
1 == 1           // true
"a"s == "a"s    // true (std::string value eq)
"a" == "a"      // pointer comparison — unreliable
JavaScript
"0" == 0    // true  — coercion, DO NOT USE ==
"0" === 0   // false — strict, use this always
null == undefined  // true  (== only)
null === undefined // false
[] == false  // true  — do not ask why
TypeScript
// TS won't always catch == on mismatched types
// always use ===
"0" === 0  // false — TypeScript flags this as error
null === undefined // false

// strict null checks catch most nullability issues
// enable strictNullChecks in tsconfig
Floating point (same as Java/C++) same issue, worse
Java
0.1 + 0.2 == 0.3 // false — IEEE 754
// use BigDecimal for money
C++
0.1 + 0.2 == 0.3 // false — IEEE 754
// no BigDecimal — use a library
JavaScript
0.1 + 0.2 === 0.3  // false
0.1 + 0.2          // 0.30000000000000004

// ONE number type = no int type
// integer overflow doesn't happen for most ranges
Number.MAX_SAFE_INTEGER // 9007199254740991
TypeScript
0.1 + 0.2 === 0.3  // false (same runtime)

// use BigInt for large integers
const big: bigint = 9007199254740992n;

// for money: store as integer pence/cents
// or use a decimal library
typeof null === "object" — This is a decades-old bug in JS that can never be fixed for backwards compatibility reasons. Always check value === null explicitly, not typeof value === "object".
Ecosystem
Tool Equivalents
Your muscle memory around tooling will need remapping. The JS ecosystem moves faster and fragments more.
Java → Build / Package Manager
Maven / Gradle
npm pnpm ★ yarn bun
pnpm is recommended for monorepos. package.json = pom.xml. node_modules = local .m2. Lock files are mandatory — commit them.
C++ → Build System
CMake / Make / Bazel
vite ★ esbuild webpack rollup turbo
Vite for dev. Rollup/esbuild for library builds. Turborepo for monorepos. There is no single standard — pick based on context.
Java → Runtime
JVM
Node.js ★ Deno Bun Browser
Node is the default server runtime. Browser is its own environment with different APIs. Deno/Bun are alternatives with native TS support.
Java → Testing
JUnit / Mockito
vitest ★ jest playwright testing-library
Vitest for unit/integration (fast, Vite-native). Playwright for E2E browser tests. Testing Library for component tests.
Java → Type System / Linting
Compiler / Checkstyle / PMD
TypeScript ★ ESLint Prettier Biome
TypeScript for types. ESLint for rules. Prettier for formatting. Biome combines linting + formatting in one fast tool.
Java → HTTP Client / Server
Spring Boot / Servlet / OkHttp
fetch ★ axios express hono fastify
fetch is built-in everywhere now. Express for servers (legacy-ish). Hono/Fastify for modern, typed HTTP servers.
C++ → Package Registry
Conan / vcpkg
npmjs.com ★ jsr.io
npm registry has ~2.5M packages. Quality varies enormously. JSR is a newer typed registry. Vet your deps — the ecosystem has a left-pad problem history.
Java → Dependency Injection
Spring DI / Guice / CDI
manual ★ tsyringe inversify Context (React)
DI frameworks exist but are far less common. JS module imports are often sufficient. In frontend, React Context or Zustand replace service injection patterns.
Java → Logging
SLF4J / Logback / Log4j
console ★ pino winston
console.log is used far more casually than in Java. For production server logging, Pino is fast and structured (JSON output).
Java → TS Config
pom.xml / build.gradle
tsconfig.json package.json
tsconfig.json controls compiler options. Enable strict: true. Set target, module, paths. Most frameworks give you a base config to extend.
Ecosystem
UI Frameworks
If you're coming from a GUI or web UI background, here's how the major Java/C++ UI toolkits map to JS frameworks.
Java Swing / JavaFX → Component UI
Swing / JavaFX
React ★ Vue Svelte Solid
React is the most widely adopted. Component model (reusable, composable UI elements) maps reasonably to Swing components. State management replaces MVC models.
C++ Qt → Desktop-class UI
Qt / wxWidgets / MFC
Electron + React Tauri + Svelte React Native
Electron wraps a browser in a desktop shell (heavy). Tauri does the same with a native webview (lighter, Rust core). Qt's signal/slot maps roughly to event handlers + state.
Java Spring MVC → Full-stack Web
Spring MVC / Thymeleaf / JSF
Next.js ★ Nuxt SvelteKit Remix
Next.js (React) is the dominant full-stack framework. Server-side rendering, routing, API routes in one project. Replaces the Spring MVC + template engine pattern.
Java → State Management
MVC Model / Bean / Service
useState/useReducer Zustand ★ Jotai Redux
Start with React's built-in hooks. Add Zustand for shared state across components. Redux is the "enterprise" choice but has significant boilerplate overhead.
Java → Data Fetching
RestTemplate / Feign / WebClient
TanStack Query ★ SWR RTK Query
TanStack Query handles caching, loading states, error states, refetching — everything you'd wire manually. Replaces service layer patterns in frontend code.
C++ OpenGL/Vulkan → Canvas / GPU
OpenGL / Vulkan / DirectX
WebGL WebGPU Three.js ★ Babylon.js
WebGPU is the modern GPU API (compute + render). Three.js abstracts WebGL into a scene graph — closer to a game engine API than raw GL calls.
Framework comparison — React has the largest ecosystem and job market. Vue has a gentler learning curve and better docs. Svelte compiles away the framework (no virtual DOM, smallest bundle). Solid is the performance option. If you have no constraint, start with React.
